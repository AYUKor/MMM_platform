# Исторические кампании: серверный контракт A2

Модельная оценка эффекта кампании с учётом фактически проходившей параллельной рекламы.

A2 добавляет автономный пакетный расчёт и чтение сохранённых результатов. Прогнозы,
существующая история расчётов и сценарии продолжают использовать прежние контракты.
Интерфейс и настройки работающего приложения этим изменением не переключаются.

## Состав и запуск

- `02_Code/01_PyMC/mmm_core/historical_campaigns.py`: paired response, проверка денег,
  календаря, обязательных физических входов и контекст четырёх моделей РТО.
- `04_Web_app/services/historical_campaign_batch.py`: пакетный расчёт, контрольные
  значения, контрольные точки, подготовка готовых JSON/Excel и публикация manifest.
- `historical_campaign_dataset.py`: чтение результатов без загрузки расчётного кода.
- `historical_campaign_report.py`: Excel на существующем стеке openpyxl; текст
  источника экранируется от формул, суммы остаются числами, файл повторно открывается.
- `contracts/historical_campaigns_v1.schema.json`: публичный формат 1.0.0;
  OpenAPI 1.12.0 и типы генерируются штатным `npm run generate:contracts`.

Из корня репозитория, с явно заданными локальными путями:

```sh
python -B 04_Web_app/services/historical_campaign_batch.py \
  --input-manifest "$INPUT_MANIFEST" \
  --package-root "$PACKAGE_ROOT" --data-root "$DATA_ROOT" \
  --source-root "$SOURCE_ROOT" --output-root "$OUTPUT_ROOT" \
  --dataset-id historical_example_v1 --max-campaigns 4

# Повторить ту же команду без --max-campaigns и с --resume.
```

`--max-campaigns` создаёт контрольную точку, не уменьшает число draws. После завершения
`manifest.json` делает версию неизменяемой: последующий запуск требует нового ID.
При resume сверяются идентичности входов и расчётного кода, а также файлы каждого
готового результата. Готовые кампании не пересчитываются. Кампании с ошибкой можно
повторить до публикации; после публикации нужен новый dataset ID.

Зависимости offline: numpy, pandas, pyarrow, xarray, h5netcdf/h5py, openpyxl, jsonschema.
Версии численных библиотек фиксируются в manifest. Для просмотра достаточно обычного
backend runtime: ни исходный Excel, ни панель, ни posterior ему не требуются.

## Договор входов

JSON `input-manifest` содержит `model_package_id`, `package_fingerprint`,
`posterior_draws`, `files`, `goldens`, `golden_tolerances` и при необходимости
`optional_provenance`. Каждый элемент `files` имеет `root` (`package`, `data`,
`source`), относительный `path` и `sha256`. Абсолютные и выходящие за корень пути
не принимаются. Указатели активной модели не читаются.

Обязательные роли:

| Роль | Содержимое |
|---|---|
| `panel` | Исходная ежедневная панель |
| `registry`, `spend` | Проверенный реестр и исторически распределённые расходы |
| `source_manifest` | Происхождение принятого кеша распределения A1/B1 |
| `source:<role>` | Все физические исходные данные, указанные в этом manifest |
| `model_manifest`, `run_config` | Идентичность модели и замороженная конфигурация |
| `fit_design_metadata`, `fit_design_row_index` | Структура и точные строки обучающих выборок |
| `denominators` | Сохранённые ежедневные population/users/orders |
| `transform:<fit>`, `posterior:<fit>` | Для каждого из четырёх turnover fits |

Формат входного кеша принят из A1: `A1_CAMPAIGN_REGISTRY.parquet` и
`A1_ALLOCATED_CAMPAIGN_SPEND.parquet`. Это входной договор, а не runtime import
исследовательского скрипта. Число кампаний и конкретные ключи не зашиты в код.
Исходные строки и их распределение сохраняются в принятом исходном кеше, связаны
его manifest и остаются локальными; A2 их не изменяет и не объединяет поставки.
Исторический SHA кода `data_pipeline` является provenance, не требованием
восстановить оригинальный checkout обучения.

`goldens` задаётся извне: ключ кампании → `budget`, `rto`, `roas`, `during`, `after`.
Для эффектов и размена передаются `p10/p50/p90`; `golden_tolerances` задаёт абсолютные
допуски до запуска. Неуспех любого обязательного эталона запрещает публикацию.
Локальная реальная приёмка дополнительно сравнивает сохранённые дневные и
географические draws с принятым A1. Публичные тесты используют искусственные данные.

## Метод и состояния

Расходы выбранной кампании вычитаются из фактической истории. Параллельные расходы,
контроли, ежедневные пользователи и параметры остаются теми же. Применяются
сохранённые `spend / population_k / x_scale_geo`, нормированный adstock с лагами
от 0 до L включительно, насыщение и масштаб целевого показателя A1. Новой модели,
новых priors, шумов наблюдений или нормирования по будущему каталогу нет.

Размен = дополнительный РТО / полный исходный бюджет. Допуск покрытия — 0,01 руб.
Сначала суммируются эффекты одного draw, затем считаются P10/P50/P90. Это условная
на наблюдаемых пользователях модельная оценка: привлечение новых клиентов отдельно
не оценивается. Ограниченный статус модели сохраняется.

Три независимые характеристики записи:

- `identity_status`: `confirmed` для одной однозначной записи с одним корректным
  объявленным периодом; `needs_review` для нескольких/некорректных периодов.
- `coverage_status`: `full` либо `unavailable` с отдельными причинами.
- `result_status`: `pending`, `calculated`, `unavailable`, `error`.

Несколько периодов не делятся по разрывам дат и не объединяются произвольно.
`source_group_id`, устойчивый `campaign_key`, подтверждённый `business_campaign_id`
и `declared_windows` отделены от фактических `start_date/end_date`. Исправленная
поставка не создаёт новый ключ только из-за изменения SHA файла: источник версии
учитывается отдельно, ключ принятого кеша сохраняется. Новые пространства имён
источников не смешиваются по названию.

Недостаток денег, неподдерживаемый канал, пропуски календаря, отсутствие предыстории
или хвоста, выход за обучение имеют отдельные причины. Кампания не обрезается,
даты не заполняются нулевыми расходами, будущие аналоги не подставляются.
`evaluated_budget_rub` означает бюджет, покрытый строками и каналами модели;
сам факт выполнения определяется только `result_status`.

Карточка содержит полный/распределённый/покрытый панелью/покрытый моделью бюджеты,
исторические географии, фактические и объявленные периоды, `tail_days`, результаты,
ограничения и версию модели. У недоступной оценки `result: null`, а не ноль.

## HTTP и будущий интерфейс

| GET | Содержимое | Разрешение |
|---|---|---|
| `/api/v1/historical-campaigns` | Реестр четырьмя блоками | `calculation.read` |
| `/api/v1/historical-campaigns/{campaign_key}` | Карточка, включая причины недоступности | `calculation.read` |
| `/api/v1/historical-campaigns/{campaign_key}/daily` | Готовый дневной РТО | `calculation.read` |
| `/api/v1/historical-campaigns/{campaign_key}/media` | Фактический план; итоги geography/channel и geography×channel | `calculation.read` |
| `/api/v1/historical-campaigns/{campaign_key}/report.xlsx` | Подготовленный Excel | `report.download` |
| `/api/v1/contracts/historical-campaigns-v1.json` | JSON Schema | существующая политика контрактов |

Используются существующая сессия, центральные permissions и механизм безопасного
скачивания `_binary`, включая Content-Disposition. Не создаётся второй auth слой.
Ошибки: 401/403 — существующая авторизация; 422 `HISTORICAL_QUERY_INVALID`;
404 `HISTORICAL_NOT_FOUND` либо `HISTORICAL_VERSION_UNAVAILABLE`;
409 `HISTORICAL_RESULT_UNAVAILABLE` либо `HISTORICAL_DATASET_CORRUPT`.
Ошибки файлов не раскрывают пути и traceback и не включают fallback старой версии.

Параметры: `dataset_id` у всех методов; у реестра `q`, `sort` (`start_date`,
`end_date`, `source_budget_rub`, дополнительно `campaign_name`), `order` (`asc/desc`),
`offset` (с 0), `limit` (1–100). Поиск без учёта регистра и сортировка применяются
к полному набору до пагинации. Страница независима для каждого блока; `total`
означает число совпадений в блоке. Tie-break — `campaign_key` по возрастанию;
отсутствующие значения всегда последние. Порядок: Доставка ТС5, Доставка ТСХ,
Магазины ТС5, Магазины ТСХ. Общей суммы по четырём направлениям нет.

A1_PRODUCT_SPEC остаётся основой будущего раздела. Нужны поиск по названию, даты,
бюджет, четыре блока и знакомая подача страницы прогнозов. Дополнения A2:

- Малый размен отображлять минимум с четырьмя десятичными знаками; полное значение
  доступно в подробностях. API не округляет числа.
- Медианы `during` и `after` не обязаны давать медиану `rto`. Не рисовать их как
  складывающиеся части медианы; равенство проверяется на уровне каждого draw.
- P10/P50/P90 — распределение одного результата, не три разных медиаплана.
- Нельзя строить geography×day срез из готовых дневных и географических квантилей.
- `matches_active_model: false` означает сохранённый результат другой модели;
  он остаётся доступным с исходным `model_package_id`. `null` — активный ID не задан.
- Не вводить произвольный балл надёжности и не подменять отсутствие оценки нулём.

## Хранение и будущая материализация

Расчёт пишет `<output_root>/<dataset_id>/`:

```text
manifest.json                 # публикация только после технических проверок
progress.json                 # идентичность, длительность, память, checkpoints
private/input_manifest.json   # локальная provenance; не для HTTP
private/parameters/*.npz      # локальные параметры; не переносить для просмотра
private/<campaign_key>/*      # draws, проверки или отдельная ошибка
serving/registry.json
serving/<campaign_key>/daily.json
serving/<campaign_key>/media.json
serving/<campaign_key>/report.xlsx
```

Manifest фиксирует формат, метод, dataset/run ID, модель, панель, все входные SHA,
расчётный код, версии библиотек, статусы и SHA/размер каждого serving/private файла.
В Git входят только код, контракты, искусственные тесты и эта инструкция.

Для **будущей** материализации точное относительное размещение:
`04_Web_app/data/historical_campaigns/<dataset_id>/{manifest.json,serving/**}`.
Private/raw/posterior не нужны серверу. Предусмотрены необязательные поля backend
config: `paths.historical_datasets_root = "04_Web_app/data/historical_campaigns"`
и `historical_campaigns.dataset_id`. В A2 работающие configs не изменяются.
После будущего копирования, до включения конфигурации:

```sh
PYTHONPATH=04_Web_app python -B -m services.historical_campaign_dataset \
  --root 04_Web_app/data/historical_campaigns --dataset-id historical_example_v1
```

Команда проверяет содержимое по хешам, JSON-контракты и действительную доступность
каждой карточки, дневного ряда, медиаплана и отчёта. Одного количества файлов
недостаточно. Затем требуется HTTP-приёмка с авторизованной сессией. Перенос и
выпуск выполняются отдельным этапом по END_TO_END_CHANGE_LIFECYCLE.md.

## Приёмка и передача

В CI: физически полный искусственный пакет четырёх fits, paired formula,
неизменная параллельная реклама, пропуски/хеши, resume, изоляция ошибок, поиск,
сортировки/пагинация/null, перезапуск процесса, реальные GET и числовой Excel,
permissions и прежние backend/frontend regression suites.

Локальные материалы A2 содержат мост независимой проверки A1 `_01` к принятому
`_02`, точные входы, четыре численных эталона, результаты полного пакета и HTTP
приёмку. Независимая проверка A1 пересчитывала три пары chain/draw на кампанию;
по всем draws она повторяла агрегирование сохранённых эффектов. Это не заявление
о независимом пересчёте всего posterior.

Handoff to ChatGPT: серверные контракты и данные подготовлены. Следующая задача —
интерфейс «Прошедшие кампании» на этих read-only API, затем локальная приёмка
владельцем и привычный release lifecycle. Merge выполняет владелец.
